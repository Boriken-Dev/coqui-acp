### Added

- `coqui-acp-pi`: a `pi-api-key` account whose `variable` is `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY` or `XAI_API_KEY` provides the API that variable carries a key of (`anthropic-api`, `openai-api`, `gemini-api`, `xai-api`), so a host lists it beside the other accounts of that API and any harness that takes the API can use the key (the credential stays `api_key`); a key of any other variable, an OAuth token or a bearer token provides nothing, as before. `coqui_acp_harness::stdio::accounts::Setting::provides` pairs a value of a setting with a standard, the kind's schema marks that property `"x-provides-by-value"` (`PROVIDES_BY_VALUE`: an object from each value to a list of standards), and `accounts::provided(info, settings)` is the standards an account provides, the kind's own when its setting is absent or unlisted (`coqui_acp_api::PROVIDES_BY_VALUE` names the annotation). The account provider still keeps no `pi-api-key` account: the kind is what Pi applies a key as, so only a host that makes one reads the annotation.
- `coqui-acp-secrets`: a request waits only as long as someone can answer. `secret_request` takes `wait_seconds`, a `Frontend` says whether the person is there (`Frontend::attended`) and the longest it waits (`Frontend::longest_wait`, stated as the maximum of `wait_seconds` in the tool's schema) and gives up on a question after the agent's limit (`Frontend::request_within`). The status says what happened: `accepted`, `declined`, `cancelled`, `timed_out` or `no_one_present` (answered at once, asking nothing, unless the frontend already holds every secret asked for).
- `coqui-acp-secrets`: a `Frontend` can hold secrets. `Frontend::recall` answers a `secret_request` whose questions are all secret ones it holds without asking the person (`Event::Recalled`), `Frontend::keeps` adds a `_keep` question (`KEEP_FIELD`, `Keep`) that offers the person how long a typed secret is kept, and `Frontend::remember` is told each typed value with the way chosen. All three have defaults that do nothing, so a frontend that holds nothing is unchanged.
- `coqui_acp_harness::stdio`: OpenCode (`opencode acp`) takes accounts and exports its sessions. `StdioHarness::OpenCode` and a provider of its own, `OpenCodeProvider` (id `opencode`) with `OpenCodeAccounts` (id `opencode_accounts`), keep the stdio provider's machinery with the harness fixed. Accounts run OpenCode with `XDG_DATA_HOME` set to the account's folder, so its sign-in (`opencode-login`: `auth.json`, watched) and its sessions are the account's; `opencode-api-key` applies a key of an accepted API standard, and `opencode-provider-key` is a key read from any variable the account names (fourteen providers' are suggested in the sign-in form), made by the `api-key` sign-in. The `provider-key` and `provider-code` sign-ins run OpenCode's own `opencode auth login` for a provider over plain pipes and answer what it asks (a key typed on one line, a code shown with its page), keeping the `auth.json` it wrote as an `opencode-login` account; a browser flow that returns to a port on the machine OpenCode runs on is refused with its reason. `export_session` reads `opencode export --pure <id>` into a history and pages it, and `import_session` writes a history into the account's data folder as a session OpenCode itself lists, loads and continues (`opencode import`; the session is `ses_` and the host's UUID's hex digits, which the relay turns into the UUID and back), with no account (or the machine's own sign-in) it goes into the store the environment names, through a file made in a folder of the import's own that is removed with it; it falls back to a replay as context only when `replay_max_bytes` is set and the file cannot be written (a spawner that runs programs elsewhere, or no private files in the account's folder). `coqui_acp_api::contract::Contract::imports_into_a_store` lets a provider like this one seed an empty history in the suite instead of refusing. `coqui_acp_api::standard::{OPENCODE, OPENCODE_KEY}` are the two new standards. The stand-in `fake_stdio_cli` plays OpenCode's `auth list`, `export` and a folder of sessions.
- `bindings/dart/coqui_acp_chat_ui`: what an app with its own conversation needs to draw through the package. `ChatRenderers.wide` names the entries (a table, a chart) that take the whole width rather than the column; `ChatLook.centred` puts the column in the middle of a wider space and `ChatLook.bubbleBorder` draws a line round a bubble; `AgentMarkdown` takes `inlineSyntaxes`, `builders`, `onTapLink` and `softLineBreak`, so a host gives its own words a meaning and decides what a link does. The `/` list is a keyboard's: the arrow keys move a highlighted row, Enter and Tab take it without sending, Escape closes it until the text changes, `Composer.onSuggestions` says whether it shows, `suggestionLimit` sets how many each group holds (it scrolls), and a name that starts with the word is listed before one that only holds it in its name or description; a command's `hint` follows its name. `Composer.canQueue` false shows Stop alone while a turn runs, for a host that cannot hold a message. `coqui_acp_chat`: `AgentCommandInfo.hint`, read from the command's `input.hint`.
- `bindings/dart/coqui_acp_chat_ui`: what an app with its own conversation needs to draw through the package. `ChatRenderers.wide` names the entries (a table, a chart) that take the whole width rather than the column; `ChatLook.centred` puts the column in the middle of a wider space and `ChatLook.bubbleBorder` draws a line round a bubble; `AgentMarkdown` draws a link in the look's accent and takes `inlineSyntaxes`, `builders`, `onTapLink` and `softLineBreak`, so a host gives its own words a meaning and decides what a link does. - `coqui_acp_claude::accounts::apply` and `coqui_acp_codex::accounts::apply` (`apply_with`, `ApplyOptions`) apply an `AccountGrant` to a `ClaudeLaunch` or `CodexLaunch` through the files of a spawner, as the providers' `start`, `models` and `usage` do (they call the same function): credential variables cleared, the kind's set, Codex's key or token saved by `codex login` on standard input, and `Applied::hold` placing and watching a login the grant carries. A login kind whose grant carries no copy of its file and has a `state_dir` is applied in place (the host's own directory, nothing written). `coqui_acp_harness::account::Files::spawner`.
- `coqui-acp-api`: `AccountCatalog::secret_variables`, the part of `credential_variables` whose value is itself a secret (a key, a token, a password, a private key), so a host can refuse those without refusing an endpoint, a cloud-provider switch or a region; Claude Code and Codex list theirs, and the contract checks every name is also a credential variable.
- `coqui-acp-hub`: a hub's log can outlive the host's restart. `Hub::log_snapshot` (`LogSnapshot`, with `to_json` and `from_json`) and `Hub::log_after` give the host the kept updates, and `Builder::restore_log` starts a hub with them, so its head and every cursor a client holds stay valid and prompt numbers go on. A `session/load` or `session/resume` whose cursor is past the head (from a log that is gone), older than the log kept, or not a cursor is now a JSON-RPC error (`-32602`, `error.data.reason` `cursor_ahead`, `cursor_expired` or `bad_cursor`) that attaches nothing. Before, a cursor past the head replayed nothing, an older one replayed from the oldest entry kept with `truncated` set, and a non-cursor was taken as none.
- `coqui_acp_harness::set_program_dirs`: folders searched after this process's `PATH` for the program of a launch whose environment sets `PATH`.
- `coqui_acp_harness::Access` (`Sandbox` none, workspace or read-only; `network`; `Approvals` ask, edits or never; `Access::STANDARD` is no sandbox, the network on, ask) and the `_meta` key `dev.boriken.coqui.acp/access`: one access in words every harness shares. `coqui-acp-codex` turns it into the approval policy (`untrusted`, `on-request`, `never`), the sandbox (`danger-full-access`, `workspace-write`, `read-only`) and the workspace sandbox's `network_access` (`CodexLaunch::apply_access`); `coqui-acp-claude` into the permission mode (`default`, `acceptEdits`, `bypassPermissions`, `plan` for a read-only sandbox) and Claude Code's sandbox settings through `--settings` (`ClaudeLaunch::effective_permission_mode`, `access_settings`); `coqui-acp-pi` into the mode its gate starts in (`PiLaunch::start_mode`). Each provider's settings take `access` and `allow_client_access` (a client's own `_meta` access replaces it; default false); `CodexAgent`, `ClaudeAgent` and `PiAgent` take `client_access(bool)`. With no access given, nothing is sent and each command line's own settings decide, as before.
- `coqui_acp_claude::accounts::variables` and `coqui_acp_codex::accounts::variables` list, for an `AccountGrant`, the variables applying it sets in the harness's environment that hold no credential: Claude Code's `CLAUDE_CONFIG_DIR` (a login kind with a directory) and `ANTHROPIC_BASE_URL`, and Codex's `CODEX_HOME`. A host reads them before a session starts, so its profile's layers can see what an account gives the program; nothing is applied, and a grant a provider cannot apply lists none.
- `coqui_acp_harness::{Target, Translation, Part}` and `Access::translate(Target)`: the one table that turns an access into each harness's words, for Claude Code, Codex, Pi, Grok, Antigravity and OpenCode: the harness's own word (Codex's sandbox and approval policy, the permission mode, Grok's sandbox profile), the arguments, variables and JSON a program is started or opened with, and the words that say what became of each setting or why the harness cannot express it. Grok takes the sandbox as `GROK_SANDBOX` and `never` as `_meta` `yoloMode`; Antigravity takes a workspace or read-only sandbox as `--sandbox` and `never` as `--dangerously-skip-permissions`; OpenCode takes its permissions as the one variable `OPENCODE_PERMISSION` (a read-only sandbox denies edits, `edits` allows them and asks for commands, `never` allows everything) and has no sandbox. The Claude, Codex and Pi launches read it, so a host that reports what became of an access reads the same table.

### Fixed

- `coqui-acp-harness` and `coqui-acp-bridge` on Windows: a program that had already ended when it was to join its job object no longer fails the start. The system refuses such a process with "access denied", which showed as `Failed to assign job` now and then under load; it is now nothing to contain and starts as usual, its status readable. Any other refusal names the system's own error.

### Added

- `coqui-acp-hub`, a new crate: one live ACP session held independent of any client and served to any number of attached clients, with no I/O of its own. `Hub` takes the agent's and each client's JSON-RPC messages and returns the messages to send. A client attaches with `session/load` (replay from the start or from a cursor) or `session/resume`; updates are logged, bounded by `Settings` (`max_log_entries`, `max_log_bytes`) with an opaque, monotonic `Cursor` carried in `_meta["dev.boriken.coqui.acp/hub"]`, and fanned out live; prompts from every client queue in order, stamped with the sender, behind a running turn; a permission request goes to the clients a host `Policy` lets answer, the first valid answer wins and the rest are told (`Note::PermissionAnswered` names who answered; `permission_window_ms` makes `poll` report one that waits, and the hub never answers it itself); detaching never ends the session, and `attached_count` and `last_activity` are what a host ends one from. Clients are identified by the host (`Client`: id, label, role, subject). The extension notifications are `_dev.boriken.coqui.acp/hub_presence`, `hub_turn_ended`, `hub_permission_closed` and `hub_ended`.
- **A forwarded `session/cancel` names its session in the page scope's answer.** `Scope.fromPage` returns `cancelled` with it, so a provider can close the window asking about that session's permission request and answer the agent `cancelled`.

- `coqui-acp-api`: the `account_provider` kind (`AccountProvider`, with the object kind `account_watch`, `AccountWatch`), so sign-in, renewal, watching and plan usage belong to an account provider and not to an ACP harness. It `describe`s itself, lists what it `offers` (the account kinds, each with the standards it `provides`, the login methods and the kinds that report usage), runs `login` as the harness's was (spawner and prompter, cancel and timeout answered `GONE`), `renew`s, `watch`es an account's credential files and tells a keeper of a renewal or loss (the returned `AccountWatch` stops it), and answers `usage` with `AccountUsage`: the plan's windows, used, resets and models, or "not offered". `AccountUsage` holds no session's tokens: those stay with ACP, as the session's usage updates. New kinds with their own floor hashes, schemas in `include/coqui_acp_api.schemas.json`, the kinds in `include/coqui_acp_api.kinds.json` and `python/coqui_acp_api_kinds.py`; `contract::AccountContract` and the program `acp-account-check` hold a provider to it; `examples/echo_account_provider.rs` and `examples/provider-python/account/` are the echoes in Rust and Python. The harness kind and its hash do not change; moving each harness's sign-in off it is later.
- Plan limits read on demand by the account's side, with no session, no turn and no harness: `coqui_acp_claude::account_usage::read_limits` (Claude Code's `/api/oauth/usage` with a subscription login's access token: the five-hour and weekly windows and a window per model), `coqui_acp_codex::account_usage::read_limits` (the ChatGPT backend's `/wham/usage` that Codex's `account/rateLimits/read` reads, with its account id, and no `codex` process) and `coqui_acp_pi::account_usage::read_limits` (Pi reports none). - `coqui-acp-bridge`: `mcp-config` and `mcp-shim --peer`, so an MCP client with no ACP session reaches a peer's own tools from one stable entry. A peer keeps a stream of `mcp-offer/1` standing, with the metadata `standing/1`, and each program gets a stream of its own.
- `coqui-acp-page`, and `package:coqui_acp/page.dart` for Dart: a person's agents from a page, over `document.acp`.
- `coqui-acp-bridge`: `serve --linger` keeps a link's agent for a time and gives it back to the same proven peer on a new connection, while the store still accepts that peer, with `--linger-per-peer`, `--linger-total`, `--linger-buffer-bytes` (at most 256 MiB) and `--linger-settle-ms`. Off by default. Output dropped while nobody was connected is said in a `_dev.boriken.coqui.acp/output_lost` notification, first on the next link, and what a kept agent wrote before it ended still goes to its peer. On Unix a helper, `agent-guard`, cleans up a kept agent's process group if the bridge goes; it is cleanup, not containment.
- `coqui-acp` and `coqui_acp` for Dart: `Event::OutputLost` and `AcpOutputLost` report `_dev.boriken.coqui.acp/output_lost`.
- `coqui-acp`: `Builder::ends_turn` says which extension notifications end a turn, so a connection ending after one is no `Event::Failed`, and `Builder::disconnect_detail` says what became of a lost agent, in that event's text. Turns are counted, so a turn sent before the last one's ending arrived is still running when that ending comes.
- `coqui-acp-provider`: `Settings::options`, with `StartOption`, `OptionValue` and `OptionTarget`, for the models, efforts and modes a host lets a client choose. `AcpFacade` answers them in `session/new` and `session/resume` as ACP's `configOptions`, the one of category `mode` also as `modes`, and takes `session/set_config_option` and `session/set_mode` until the provider starts, so `coqui_acp`'s `Builder::model` and `Builder::effort` reach `StartRequest`. A value outside the host's list is refused, there and in the launch `_meta`; a change after the provider started is refused. `Error::Settings` for options that cannot be served.
- `coqui-acp`: `Exchange::describe`, with `Description` and `Answer`, says what an agent offers before any session: its start options as ACP's `SessionConfigOption`s, its modes as `SessionModeState`, and its sessions from `session/list`, each `Known`, `Unknown` with the agent's reason, or `NotSupported` when the agent does not advertise it, in which case nothing is sent. Options and modes come from the `_coqui_acp/session_options` request, sent only to an agent that advertises `dev.boriken.coqui.acp/session_options` in `agentCapabilities._meta` (`SESSION_OPTIONS_METHOD`, `SESSION_OPTIONS_CAPABILITY`). What the agent answers is bounded and kept as data.
- `coqui_acp` for Dart: `AcpClient.describe`, with `AcpDescription` and `AcpKnown`, `AcpUnknown` and `AcpNotSupported`, the same for version 1 and version 2 agents; `vectors/describe.json` holds both clients to one contract. `AcpFailure.code` is the agent's JSON-RPC error code.
- `coqui-acp-provider`: `AcpFacade` advertises and answers `_coqui_acp/session_options` from `Settings::options`, with what the host did not declare as unknown, and `session/list` with the connection's own open sessions.
- `coqui-acp` and `coqui_acp` for Dart: what `describe` keeps is a setting, `Exchange::describe_limits` with `DescribeLimits` and `AcpClient`'s `describeLimits` with `AcpDescribeLimits`, each limit taking any value: options (default 64), values per option (1024), modes (64), sessions (500) and text (4096 UTF-8 bytes). Sessions are listed page by page, following each page's `nextCursor`, up to `pages` requests (10); a later page that fails ends the list with the pages before it. The sessions are a `SessionList` (`AcpSessionList` in Dart) whose `incomplete` says why a list stops short: a later page failed, the sessions limit was reached, or the page limit was. `vectors/describe.json` carries the defaults, and a case may set its own.
- `coqui-acp` and `coqui_acp` for Dart: the size at which agent text is delivered mid-message is a setting, `Builder::text_flush` and `AcpClient`'s `textFlush`, 64 KiB of UTF-8 by default. The Dart client had no such size, so a long message could grow without limit within a turn.
- `coqui-acp`: the tool kinds a session keeps, by which `refuse_kinds` judges a later message about a tool that does not say its kind, are a setting, `Builder::max_tool_kinds`, 4096 tool calls by default and any value taken; before, one was kept for every tool call of the session. At the limit the oldest of a kind not refused is forgotten, which changes no refusal and is said once as an `Event::Notice`. One of a refused kind is never forgotten: a tool of a refused kind that cannot be kept ends the session with `Event::Failed`. The Dart client keeps no such record.
- `coqui-acp` (feature `secret`) and `coqui_acp` for Dart (`package:coqui_acp/secret.dart`): the secret-prompt extension (`docs/secrets.md`), `_coqui_acp/secret_request` and `_coqui_acp/secret_show_open` / `_coqui_acp/secret_show_deliver` between a host and the frontend of a session's owner. A secret field of a JSON Schema form (`writeOnly` or `x-sensitive`) travels sealed by HPKE (RFC 9180) to a per-request key. The key's binding, and the sender's binding of the sealed values, are made by an identity the checker already knows, for the checker, over the digest of the form as sent: an ECDSA signature for `webcrypto` identities, a Diffie-Hellman MAC for `noise` ones. Identity keys are a signer function the caller supplies, never a key handed to the library. `vectors/secret.json` holds both languages to the RFC's vector and to the extension's bytes.

### Fixed

- `coqui-acp`: a session ended by `Event::Failed` (a refused tool that ran, an event backlog) or dropped without `close` now tells the agent to stop before `on_close` runs: the drop waits, no longer than the new setting `Builder::abort_wait` (5 s by default, whatever the close grace; `on_close` runs anyway when it passes), for the agent to take `session/cancel`, and the session is marked closing before the failure is delivered, so a reader that drops it on `Failed` no longer queues a close ahead of the cancel. The agent receives one `_coqui/flush` request after the cancel and may answer it with method-not-found.

### Changed

- The `process_spawner` kind (a break, with no shim: its hash moves and every host rebuilds) has `notice(HarnessNotice)`, how a provider tells the host what is no message of the client's: `NoticeKind::Exited` (the harness ended mid-session; how, never what it last wrote), `Notice` (such as a version it was not tested with) and `Fault` (the provider's own plumbing failed). `coqui-acp-harness`: `Settings::on_notice` is `Fn(NoticeKind, &str)`; `Serving` routes it to the spawner's `notice`, so the Claude Code, Codex and Pi providers tell the host; `LocalSpawner::notices` takes a hook. The contract suite holds a provider to telling the host that a program that died did (`die` in a stand-in program), by a notice or, for a provider that relays it, by ending the connection with a failure.
- `coqui-acp-pi`, the gate after an independent verification. It decides on the path Pi will use: `paths::resolve` ports Pi 1.5.2's `resolveToCwd` (Unicode spaces, a leading `@`, `~`, `file:` URLs, Windows `/c/…` forms), held to a table printed from that Pi, so `~/.ssh/id_rsa`, `@~/.pi/agent/models.json`, `file:///…` and a UNC path hidden behind `@` or `file://` are judged as what they are; a path whose text looks rewritten is always asked about and never remembered. The credential list gains `.git-credentials`, `.config/gh`, `.azure`, `AppData/Roaming/gcloud` and Cargo's credentials. A command the gate cut for its size is never remembered or answered from a remembered rule. On Windows Pi's `PATHEXT` is `.COM;.EXE;.BAT;.CMD`, so a project's `npm.js` no longer runs when the person's Pi settings name an npm package; a `PATH` entry with `..` is resolved before it is judged. The gate cuts a long string on a code point. The "Always allow `git …`" option says it covers every `git` command, including ones that run other programs. Tests run against a real Pi when `COQUI_ACP_PI_REAL` and its siblings name one (`tests/real_pi.rs`). **Breaking:** `Scope` gains `with_home`, `indirect` and a Pi-resolved `network`.
- `coqui-acp-pi`, the permission gate hardened after a security review. The gate puts each call to the translator with the input it will run on, and the question and the decision use that input, not the stream's. Accept edits runs an edit only inside the session's directories and away from what Pi loads (`.pi`, `.git`, Pi's agent directory, credentials), and asks otherwise; Manual and Accept edits ask about a read outside the directories, and a read or an edit of a credential file (`auth.json`, `models.json`, `.ssh`, and others) is refused in every mode but Bypass. "Always allow" is kept per program for a plain command (`git …`), per tool otherwise, and offers nothing for a compound command. Each launch's gate registers a command with a nonce, and a session whose Pi did not list it is refused. A question after the run was stopped is cancelled, not asked. Pi is started with `--no-approve` (the project's extensions, settings and MCP never load), and with `isolated` (a provider setting, `--isolated`) with `--no-extensions --no-mcp`. A launch in Bypass mode needs `allow_bypass`. The gate directory is made exclusively and closed to other users, by icacls on Windows. On Windows Pi is no longer started through `cmd.exe`: npm's `pi.cmd` runs a bare `node`, which cmd.exe looks for in the project first, so the launch reads the shim's `cli.js` and starts an absolute `node.exe` (no relative or in-project `PATH` entry, never the project), and sets `NoDefaultCurrentDirectoryInExePath`. **Breaking:** `PiLaunch::launch` returns a `Result`, `PiLaunch::program` is `command`, `Policy::decide` takes the input and a `Scope`, and the gate's dialog options and title changed.
